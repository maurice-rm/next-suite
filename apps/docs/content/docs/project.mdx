---
title: Your project after create
description: The config, lock and registry types every project gets, and how to update it, create it again, replace a file, explain a file or leave next-suite.
---

A generated project is yours. Besides the app, create-next-suite writes what describes it:

| Path                     | Belongs to        | What it holds                                                                  |
| ------------------------ | ----------------- | ------------------------------------------------------------------------------ |
| `next-suite.config.ts`   | you               | the project's settings, its plugins, the plugins it disables, every answer     |
| `.next-suite/lock.json`  | create-next-suite | what the last generation ran and wrote; commit it                              |
| `.next-suite/types.d.ts` | create-next-suite | the plugins the config can name, with their options, for your editor           |
| `next-suite/plugins/`    | you               | [project plugins](#project-plugins), each a directory with a `plugin.ts`       |
| `next-suite/overrides/`  | you               | [overrides](#overrides): files that replace generated ones                     |

`package.json` gets `create-next-suite` as a devDependency, pinned to the version that created the
project, so the config is typed and `next-suite` runs from the project:
`pnpm exec next-suite explain app/layout.tsx`. `tsconfig.json` includes `.next-suite/types.d.ts`,
which its `**/*.ts` pattern skips, since that leaves out directories starting with a dot. The
linter and formatter plugins leave `.next-suite/` alone, and Knip takes `next-suite.config.ts` as
an entry.

## The config

```ts title="next-suite.config.ts"
import { defineSuiteConfig } from "create-next-suite/config";

export default defineSuiteConfig({
  project: {
    name: "my-app",
    srcDir: false,
    importAlias: "@/*",
    reactCompiler: false,
    cacheComponents: true,
  },
  // Your own plugins join these: "./next-suite/plugins/<name>", an address such as
  // "github:acme/plugins/mail#v1", or definePlugin({ … }) in place.
  plugins: ["pnpm", "tailwind", "eslint", "prettier", "github:acme/plugins/mail#v1"],
  disable: [],
  answers: {
    mail: { provider: "resend" },
  },
  // extends: a shared config to start from; not supported yet.
});
```

| Field     | What it says                                                                                        |
| --------- | --------------------------------------------------------------------------------------------------- |
| `project` | the package name and the [base settings](./options/project); `srcDir` and `importAlias` stay as created |
| `plugins` | built-in plugins by name, a plugin directory by its path, an external plugin by its [address](./plugins/sources-and-trust), or one defined in place |
| `disable` | plugins that do not run, even when `plugins` names them                                             |
| `answers` | the answer to each option, by plugin; an option without one takes its default                       |

create-next-suite writes every plugin and every answer out, so the config alone describes the
project. It writes the config once; afterwards only you change it, by hand or with
[`next-suite add` and `next-suite disable`](#add-and-disable-plugins).

### Checked in your editor

`.next-suite/types.d.ts` adds every plugin the project can use, the built-in ones and those it
was created with, to the `PluginRegistry` of `create-next-suite/config`. TypeScript checks the
config like any other file of the project, in your editor, in `typecheck` and in `next build`:

```text
next-suite.config.ts(16,5): error TS2820: Type '"eslnt"' is not assignable to type 'PluginEntry'. Did you mean '"eslint"'?
next-suite.config.ts(24,21): error TS2322: Type '"ses"' is not assignable to type '"resend" | "smtp" | undefined'.
next-suite.config.ts(24,5): error TS2353: Object literal may only specify known properties, and 'knip' does not exist in type 'PluginAnswers'.
```

When create-next-suite reads a config, it checks the same again: an unknown plugin, a disabled
plugin it does not know, two plugins of a category that takes one, or answers for a plugin the
config does not select stop the run with a message.

## The lock

```json title=".next-suite/lock.json (abridged)"
{
  "generator": { "name": "create-next-suite", "version": "2.0.0" },
  "project": { "name": "my-app", "srcDir": false, "importAlias": "@/*", "reactCompiler": false, "cacheComponents": true },
  "plugins": [
    { "name": "pnpm", "source": "builtin", "version": "2.0.0" },
    { "name": "mail", "source": "github:acme/plugins/mail#v1", "resolved": "3f2c…", "contentHash": "sha256-9a1e…" },
    { "name": "tweaks", "source": "./next-suite/plugins/tweaks", "contentHash": "sha256-77b0…" },
    { "name": "site-url", "source": "inline" }
  ],
  "disable": [],
  "answers": { "mail": { "provider": "resend" } },
  "files": { "app/layout.tsx": "sha256-4c0d…" },
  "provenance": {
    "order": ["pnpm", "mail", "tweaks", "site-url"],
    "points": {},
    "files": {
      "app/layout.tsx": [
        { "plugin": "base", "operation": "base", "kind": "own" },
        { "plugin": "seo", "operation": "layout.metadata metadataBase", "kind": "extend" }
      ]
    }
  }
}
```

- `plugins`: where each plugin came from. A built-in plugin has the version of create-next-suite;
  an external or project plugin the [content hash](./plugins/sources-and-trust#trust) of its files
  and, for a remote one, the commit, version or archive its address resolved to; a plugin defined
  in the config is `inline`.
- `answers`: every answer, defaults included.
- `files`: a hash of every file the generation wrote, as the run left it: after the project's own
  post-steps such as its formatter, so a file you have not touched matches it. The config and
  everything under `next-suite/` are yours and not listed.
- `provenance`: which plugin did what to each file, in order; [`next-suite explain`](#explain)
  reads it.

The lock records what ran; it trusts nothing. Which sources and contents you trust stays in your
user configuration, so a project someone else wrote never runs a plugin you have not trusted.

## Update

Change `next-suite.config.ts`, then run `next-suite update`: a different answer, a plugin more or
fewer, a new override or a changed project plugin reach the project's files, and your own changes
to those files stay. [`add` and `disable`](#add-and-disable-plugins) change the config and update
in one step.

```bash
pnpm exec next-suite update
```

The update works in these steps:

1. It checks the Git working tree. A change outside `next-suite.config.ts` and `next-suite/`
   stops it: commit or stash it first. `--force` updates anyway and first saves your uncommitted
   changes to tracked files in a stash commit, whose id it prints; `git stash apply <id>` brings
   them back. Untracked files are not saved.
2. It generates the **old output**, the files as the last generation wrote them, once more: from
   the config, the project plugins and the overrides of the commit that last changed
   `.next-suite/lock.json`, with the version of create-next-suite the lock names (see
   [another version](#another-version-of-create-next-suite)).
3. It generates the **new output** from the config as it is now. External plugins need your
   [trust](./plugins/sources-and-trust#trust) as on create, and a plugin whose content hash differs
   from the one the lock recorded is named in a warning.
4. It formats both outputs the way the project's post-steps, such as `prettier --write .`, did
   after create, with the formatter installed in `node_modules`, so a file you did not touch still
   matches the lock. Whether the project ran them is read from the lock's hashes.
5. It takes the difference between the two outputs into each file, by a three-way merge:

| The file                                                   | What the update does                                                      |
| ---------------------------------------------------------- | ------------------------------------------------------------------------- |
| unchanged by you, as the lock's hash says                  | replaced with the new output                                              |
| changed by you, the same in both outputs                   | left as it is                                                             |
| changed by you and in the new output                       | merged line by line with `git merge-file`                                 |
| `package.json` and other JSON without comments, both changed | merged key by key; arrays count as one value                              |
| new in the new output                                      | added; where you wrote a file at its path, merged against an empty file   |
| no longer generated, unchanged by you                      | removed                                                                   |
| no longer generated, changed by you                        | kept, and listed under "Kept"                                             |
| deleted by you, changed in the new output                  | stays deleted, and listed under "Kept"                                    |

6. Without merge conflicts it writes the new lock and registry types and runs your package
   manager's install when the dependencies changed. It never commits; review the result with
   `git diff` and commit it yourself.

The report lists every file under what happened to it: replaced, merged, added, removed, kept or
in a merge conflict. `next-suite update --dry-run` shows the same report and writes nothing.

`srcDir` and `importAlias` cannot change once the project is created; an update with a config
that changes them stops.

### Add and disable plugins

`next-suite add` and `next-suite disable` change the config for you and run the update:

```bash
pnpm exec next-suite add pino
pnpm exec next-suite add github:acme/plugins/mail#v1 --provider smtp
pnpm exec next-suite add ../shared/plugins/audit
pnpm exec next-suite disable seo
```

`add <plugin>` takes a built-in plugin by its name, or any other plugin by its path or
[address](./plugins/sources-and-trust). It appends the plugin to `plugins`, takes it out of
`disable`, and writes the answers to its options, given as `--<option> <value>` (a list
comma-separated, a yes/no option as `--<option>` or `--no-<option>`), under `answers`; an option
without one takes its default. A path is written relative to the project. An external plugin is
fetched and read without running it, and the update asks for your trust before it runs.

`disable <plugin>` adds the plugin to `disable` and drops its answers. The plugin's files go the
way the update table says: removed where you did not change them, kept where you did.

Both edit the config through its syntax tree, so your formatting and comments stay, and new code
takes the file's quotes. When the update fails before it changed a file, such as for a plugin of a
category that takes one plugin while another is selected, or an untrusted source without a
terminal to ask in, the config is restored as it was. With merge conflicts the change stays, and
`next-suite update --continue` records it. `--force` passes through to the update.

To stop using a plugin for good, `disable` it, or delete its entry from `plugins` by hand: today
both have the same effect.

### Merge conflicts

Where you and the new output changed the same or neighbouring lines, the file gets Git's markers
and the update ends with exit code 1:

```text
$ pnpm exec next-suite update
Merge conflicts:
  app/layout.tsx: 1 merge conflict, between <<<<<<< yours and >>>>>>> next-suite
next-suite: 1 file has merge conflicts; resolve them, then run `next-suite update --continue` to record the update
```

```tsx title="app/layout.tsx"
<<<<<<< yours
      <ThemeProvider attribute="class" defaultTheme="system" disableTransitionOnChange>
=======
      <ThemeProvider attribute="class" defaultTheme="dark">
>>>>>>> next-suite
```

For a key of `package.json` you and the new output both changed, the update keeps your value,
shows both and counts it as a merge conflict too:

```text
Merge conflicts:
  package.json: your value is kept where next-suite changed it too
    scripts.lint: yours "eslint --cache", next-suite "biome check"
```

Every other file is updated already. The new lock waits in `.next-suite/pending-update.json`, so
`.next-suite/lock.json` still describes the files as they were. Edit the files until no marker is
left, then record the update:

```bash
pnpm exec next-suite update --continue
```

`--continue` refuses while a file still holds a marker, then writes the lock and the registry
types and runs the install the update postponed. While an update waits, `next-suite update` stops;
to drop it instead, restore the files with `git checkout -- .` and delete
`.next-suite/pending-update.json`.

### Another version of create-next-suite

The old output has to be what the last generation wrote, so the update generates it with the
version of create-next-suite the lock names. When that is not the running version, as after you
raised the devDependency, it runs the recorded version through npm (`npm exec
create-next-suite@<version>`), from npm's cache when it is there, from the registry otherwise.

When that version cannot run, such as offline without it in the cache, the running version
generates the old output instead, and a warning says so. A file you did not change still takes
the new output. In a file you changed, a change the newer version made to its own output does not
arrive, since it is in both outputs; `git diff` after the update shows what you have.

### Limits

- Changes on neighbouring lines are a merge conflict, as in Git, even where they could both apply.
- A JSON file with comments, such as a `tsconfig.json` you commented, merges line by line.
- An external plugin whose address moved, such as a branch with new commits, generates the old
  output with its new content; a warning names it.
- When the new output adds a formatter, its files are compared unformatted until it is installed;
  run your formatter after the update.

## Create the project again

`--config` creates the project a config describes, with its plugins and overrides:

```bash
npx create-next-suite@2.0.0 --config my-app/next-suite.config.ts my-app-again
```

The result is the same project as the one the config came from, its lock included, minus your
changes to generated files. Without a directory, the project is created in a directory named
after `project.name`. The new project gets the config unchanged and a copy of everything under
`next-suite/` beside it.

The config is the only description: `--config` cannot be combined with `--answers` or `--plugin`,
and of the question flags only those about the run itself, `--no-git` and `--no-install`, are
taken. External plugins the config names still need your trust; a config is no trust declaration.

## Project plugins

A plugin of the project lives in a directory under `next-suite/plugins/` and is named in the
config by its path, such as `"./next-suite/plugins/tweaks"`. It is a plugin like any other, with a
`plugin.ts` and its files, and it may do everything an external plugin may. A plugin can also be
defined in place:

```ts title="next-suite.config.ts"
import { definePlugin, defineSuiteConfig } from "create-next-suite/config";

export default defineSuiteConfig({
  project: { name: "my-app" },
  plugins: [
    "pnpm",
    "./next-suite/plugins/tweaks",
    definePlugin({ name: "site-url", title: "Site URL", scripts: { url: "echo $SITE_URL" } }),
  ],
});
```

A plugin defined in place reads the files it names relative to the config. Project plugins and
plugins defined in place are the project's own code and run without asking for trust, as
`npm run` runs a project's scripts.

## Overrides

A file under `next-suite/overrides/<path>` replaces the generated file at `<path>` completely,
after every plugin ran: `next-suite/overrides/app/not-found.tsx` replaces `app/not-found.tsx`.
The lock records it as an operation of kind `override`. An override of a path the project does not
generate stops the run; put a file of your own straight into the project instead. Overrides hold
text only.

An override is a normal file of the project, type-checked and linted where it lies. Nothing
imports it, so once the project has overrides or project plugins, the Knip plugin adds
`"next-suite/**"` to `ignore` in `knip.config.ts`.

## Explain

`next-suite explain <file>` shows who wrote a file, whether it is still as generated, and every
operation on it in order, with its plugin and kind: `own` on a file the plugin writes, `extend`
through what the file's owner offers, `direct` for an edit of someone else's file, `override` for
an override.

```text
$ pnpm exec next-suite explain next.config.ts
next.config.ts: written by base, unchanged since it was generated
  1. base        base                                   own
  2. static-csp  nextConfig.imports ./security-headers  extend
  3. static-csp  nextConfig.options headers             extend
```

A direct edit names where its plugin came from and warns that it may break when the file's writer
changes. For a file next-suite never wrote, explain says it is entirely yours. It works from any
directory of the project.

## Eject

`next-suite eject` turns the project into a plain Next.js project: it removes
`next-suite.config.ts`, `.next-suite/` and `next-suite/`, the devDependency on create-next-suite
and the registry types in the include of `tsconfig.json`. Overrides are the project's files
already, so nothing else changes. Run your package manager's install afterwards to update the
lockfile.

While `next-suite/` holds plugins or overrides, eject lists them and stops; move them out first,
or pass `--force` to delete them too. A `tsconfig.json` with comments is left to you, and so are
the entries for `next-suite.config.ts` and `next-suite/**` in `knip.config.ts`; eject says what to
remove.
