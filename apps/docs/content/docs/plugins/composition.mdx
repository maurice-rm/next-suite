---
title: Composition points
description: How plugins add to the files they share.
---

Some files belong to no single plugin: `package.json`, `.gitignore`, `next.config.ts`, the root
layout. Plugins never write these themselves; they contribute entries under `contributes`, and the
core merges the entries of all plugins by a fixed rule.

| Point | What a plugin contributes | Rule |
| --- | --- | --- |
| `package.scripts`, `package.fields` | scripts and fields of package.json | one value per name; two different values fail |
| `gitignore` | patterns | in plugin order, duplicates dropped |
| `readme` | sections of README.md | in plugin order |
| `nextConfig` | imports, options and wrappers of next.config.ts | options once per key; wrappers nest in plugin order |
| `rootProviders` | providers around the children of the root layout | in plugin order |
| `layoutMetadata` | fields of the root layout's `metadata` | once per key |
| `cssImports` | stylesheets the global CSS imports first | in plugin order, duplicates dropped |
| `prettierPlugins` | plugins of the Prettier configuration | in plugin order, duplicates dropped |
| `lintStaged` | commands lint-staged runs per glob | grouped by glob |
| `ciChecks` | scripts the CI workflow runs | in plugin order; each script must exist |
| `agents` | sections of AGENTS.md | in plugin order |
| `allowedBuilds`, `deniedBuilds` | dependencies whose install scripts may or need not run | written in the format of the package manager |
| `stack`, `nextSteps` | the stack line and the next commands at the end of a run | in plugin order |
| `instrumentation` | functions `instrumentation.ts` runs at startup (`register`) and on server errors (`onRequestError`, export required) | in plugin order, duplicates dropped; Node.js runtime only |
| `instrumentationClient` | functions `instrumentation-client.ts` runs in the browser before the app starts | in plugin order, duplicates dropped |
| `bodyEnd` | components rendered at the end of `<body>` in the root layout | in plugin order; an export name used by two modules fails |
| `tsconfig` | `paths` and `include` of tsconfig.json | one target list per alias; two different lists or the project alias fail |
| `generatedDirs` | folders of generated code | added to `.gitignore` and to the linter and Knip ignores |
| `lint` | `ignores` of the linter | in plugin order, duplicates dropped |
| `knip` | `entry`, `ignore` and `ignoreDependencies` of the Knip configuration | in plugin order, duplicates dropped |
| `container` | build arguments, environment and compose services | once per name; a service defined differently fails |
| `csp` | sources per Content Security Policy directive | sources of a directive joined across plugins |
| `health` | checks the health route runs | once per name |
| `testSetup` | setup files of the test runner | in plugin order, duplicates dropped |
| `logRedact` | paths the logger redacts | in plugin order, duplicates dropped |

Environment variables (`env`) form their own point: `.env.example` lists them by plugin, and an env
schema reads them by scope.

The core writes `instrumentation.ts` and `instrumentation-client.ts` itself, next to `app/`, once a
plugin contributes to them. Module paths starting with `#src/`, such as `#src/lib/logger`, resolve
through the project's import alias. No built-in plugin reads `container` and `health` yet.

In addition, `conditionalContributions` adds contributions only when a condition holds.
