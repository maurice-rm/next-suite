Every choice in create-next-suite is a plugin: the package manager, the linter, the styling. A
plugin is a directory with a `plugin.ts` and the real files it adds:

```text
next-themes/
├─ plugin.ts                      what the plugin is, asks, uses and adds
└─ files/
   └─ theme-provider.tsx          a file of the generated project, as it is
```

`plugin.ts` exports `definePlugin({…})` from `create-next-suite/plugin` by default:

```ts title="plugin.ts"
import { definePlugin } from 'create-next-suite/plugin'

const VERSIONS = { 'next-themes': '0.4.6' }

export default definePlugin({
  name: 'next-themes',
  title: 'next-themes',
  description: 'Switches between a light and a dark theme.',
  options: {
    defaultTheme: {
      question: 'Which theme does a first visit get?',
      choices: ['system', 'light', 'dark'],
      default: 'system',
    },
  },
  dependencies: VERSIONS,
  files: { '@/components/theme-provider.tsx': 'files/theme-provider.tsx' },
  layout: ({ options }) => ({
    imports: [{ names: ['ThemeProvider'], from: '@/components/theme-provider' }],
    wrapChildren: {
      component: 'ThemeProvider',
      props: { attribute: 'class', defaultTheme: options.defaultTheme },
    },
    htmlAttributes: { suppressHydrationWarning: true },
  }),
})
```

Each field is a value or a function of the plugin's [context](./definition#context). TypeScript
checks the definition in your editor: a misspelled field, a default that is none of the choices or
a comparison with an answer the option cannot have fails before anything is generated.

## How a project comes together

The core starts from the [base project](../glossary), a Next.js app of real files, and lets every
selected plugin add to it:

- **Fields the core owns.** `package.json`, `.gitignore`, `.env.example`, `README.md`, the global
  stylesheet, the root layout, `next.config.ts` and the instrumentation files belong to the core;
  plugins add to them through fields such as `dependencies`, `gitignore`, `env`, `readme`, `css`,
  `layout`, `nextConfig` and `instrumentation`.
- **Files of its own.** `files` copies real files from the plugin's directory into the project,
  optionally with an [edit](./files-and-edits) once every plugin has contributed.
- **Points.** Plugins work together through [points](./points) instead of naming each other: the
  ORM tells the auth plugin how to import its client, the linter hands lint-staged the commands
  for staged files.
- **Direct edits.** `edit` changes a file another plugin or the base project writes, by code
  operations, as the escape hatch when no field or point covers it.

The plugin computes; the core writes the files, runs the processes and fetches. A plugin names
the exact version of each package it installs once, in a constant `VERSIONS` at the top of
`plugin.ts`.

## Questions and flags

A plugin with a `category` is one of the choices of that category's question; without one it is an
extra, asked with yes or no and selected with `--<name>`. Each option becomes a further question
with a flag `--<plugin>-<option>`; its `description` says in `--help` what the flag sets, and the
`description` of a choice shows as the hint beside its label. A plugin may also state a
[precondition](./definition#precondition) and `conflicts` with other plugins, each with the reason
the wizard and the error show.

## Plugins of your own

A plugin of your own is a directory with a `plugin.ts`, loaded with `--plugin <address>` from a
local directory, npm, GitHub, GitLab, Git, a tarball URL or a registry. Its questions and flags
join those of the built-in plugins. The page on [sources and trust](./sources-and-trust) says
where plugins come from and which of them may run.
